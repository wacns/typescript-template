# Standing instructions for autonomous sessions

Read this and `PROGRESS.md` before doing anything. One task per session.

## The rule that matters most

**`npm run verify` passing does not mean the change works.** It means the change compiles, lints,
and has no RAM-cost name collisions. In this project that is a weak signal: every serious defect
found so far passed all three cleanly (see the table in `PROGRESS.md`). Correctness means matching
a running game's behaviour, and you cannot observe that.

So: never describe unverified work as done, working, tested, or fixed. Say what you changed and
what a human would need to run to confirm it. Overclaiming here is worse than doing nothing,
because it invites merging code nobody has actually exercised.

## Cycle

1. **Pick one task.** Take the top unblocked item from `PROGRESS.md` → Next queue, or propose one
   and write it to `.claude-pipeline/queue/1_proposed/<slug>.md` first. Prefer changes touching
   ≤3 files — small diffs pass far more often, and are far easier to review.

2. **Branch.** `git checkout -b claude/<slug>` from an up-to-date `main`. Never work on `main`.

3. **Implement.** Match surrounding style. When touching anything that mirrors game behaviour,
   read the relevant file under `BitBurner-Src/src/` rather than recalling it — the game's
   constants and APIs change between versions, and stale recall has caused real bugs here.

4. **Verify.** `npm run verify`. On failure, fix and retry at most **twice**. If it still fails,
   stop: `git checkout main`, delete the branch, and move the task to
   `.claude-pipeline/queue/3_blocked/<slug>.md` recording what failed and the exact error. Do not
   keep trying — a third failure means the task was wrong, not the attempt.

5. **Commit** on the branch, with a message explaining *why*, not what the diff shows.

6. **Hand off.** Write `.claude-pipeline/queue/2_implemented/<slug>.md` stating: what changed, what
   `npm run verify` reported, **what remains unverified**, and the exact in-game commands a human
   should run. Update `PROGRESS.md`. Push the branch and open a PR if `gh` is available.

7. **Stop.** One task per session. Leave `main` untouched and the tree clean.

## Never

- Merge to `main`, force-push, `git reset --hard` on `main`, or amend others' commits
- Edit `src/SphyxOS/**` — vendored, overwritten by `npm run update:sphyxos`
- Edit `BitBurner-Src/**` — a submodule; edits dirty it against its own upstream (hook-denied)
- Edit `NetscriptDefinitions.d.ts` — regenerated by the game on every filesync connect
- Edit `dist/**` — build output
- Weaken a check to make it pass: no disabling eslint rules, no `@ts-ignore`, no adding a name to
  `ZERO_COST_ALLOWED` in `build/check-ram-collisions.js` unless you have confirmed in
  `BitBurner-Src/src/Netscript/RamCostGenerator.ts` that its cost really is 0
- Claim in-game verification you did not perform

## Naming trap specific to this project

Bitburner bills a script's RAM by resolving every identifier against the whole ns API tree **by
name, ignoring namespaces**. A local function called `workForFaction` is charged as
`ns.singularity.workForFaction` — 48GB — with no error anywhere. On a fresh BitNode home is 8GB, so
this does not slow a script down, it makes it unrunnable.

`npm run check:ram` catches declarations. It cannot catch every case, so before naming a function,
variable, loop counter, or object key after a game concept, check it against
`BitBurner-Src/src/Netscript/RamCostGenerator.ts`.

## Useful commands

```
npm run verify        tsc + eslint + RAM-collision check   (the gate)
npm run check:ram     RAM-collision check alone
npm run lint          eslint alone
```

In-game, for a human — not available to you:

```
run WacnOS/autopilot/selftest.js            31 checks, read-only
run WacnOS/autopilot/selftest.js --active   also drives the UI
mem <script>                                measured RAM, the real ground truth
```
